# ezphot 측광 실행 오케스트레이터

이 하네스는 ezphot 레시피로 측광을 돌려 결과를 받는 흐름이다. 코드는 바꾸지 않는다.
실행 모드는 두 가지다.
- **격리 모드(기본)**: 산출물이 격리 HOME(`<iso>`)에만 생긴다. 실행이 끝나도 `<iso>`를 지우지 않고 요약만 `_workspace/runs/`에 복사하며, 삭제는 사용자가 정한다.
- **실제 아카이브 모드**: 사용자가 대상 타일마다 승인하면 실제 HOME으로 돌려 산출물을 실제 아카이브에 남긴다(다른 프로젝트가 쓸 수 있게). 조건은 `ezphot-safety` 3절.
모드는 1단계에서 사용자에게 묻는다(질문 예: "결과를 격리 디렉터리에만 둘까요(권장, 시험·확인용), 실제 아카이브에 남길까요(운영 처리, 타일별 승인)?").

리더(메인 에이전트)가 이 스킬을 따른다. 리더는 입력 탐색(읽기 전용 `find`·`ls`)과 계획 작성까지 직접 하고, 실행은 하지 않는다.

## 실행 모드: 서브에이전트 위임 (순차)

| 단계 | 담당 | 이유 |
| --- | --- | --- |
| 1. 입력·계획 | 리더 | 사용자와 범위를 맞추며 정해야 한다 |
| 2. 안전 감사 | `ezphot-safety-auditor` | 독립 판정 |
| 3. 실행 | `ezphot-runner` | 감사된 명령을 순서대로, 오래 걸림 |
| 4. 측광 QA | `photometry-qa` | 측광적 판단 |
| 5. 보고·갤러리 | 리더 | |

단계 사이에 대화가 필요 없으므로 지속형 에이전트를 쓰지 않는다. 여러 대상·필터를 한꺼번에 돌릴 때도 `<iso>`를 대상별로 나누고 runner를 대상별로 한 번씩 부른다(같은 `<iso>`에 동시 실행 금지).

## 작업 디렉터리

`ezphot/_workspace/`. 새 요청이면 기존 `_workspace/`를 `_workspace_<YYYYmmdd_HHMMSS>/`로 옮긴다(이전 실행 요약 보존).
실행 요약은 `_workspace/runs/<obj>_<tag>/`, `<tag>` = `YYYYmmdd_HHMMSS`.

## 요청 명확화 (0단계보다 먼저)

1. 요청을 CLAUDE.md 「요청이 모호할 때」 기준과 그 프로젝트의 "자주 모호한 것" 목록으로 점검한다.
   코드·문서·`_workspace` 기록을 읽어 스스로 답할 수 있는 것은 먼저 확인한다(읽기 전용).
2. 남은 모호함은 AskUserQuestion으로 묻는다: 질문 최대 4개, 질문마다 선택지 2–4개, 권장안을 첫 번째에 두고 이유를 적는다.
   질문 앞에 무엇을 확인했는지 한두 줄로 밝힌다.
3. 답과, 묻지 않고 가정한 것을 기억해 두었다가 1단계에서 `_workspace/00_input/request.md`의 "## 확인한 사항", "## 가정"에 적는다.
4. 모호함이 없으면 묻지 않고 바로 0단계로 간다. 1단계 이후(영향 분석 결과 등)에 생기는 질문은 그 단계에서 묻되, 이미 답한 것을 다시 묻지 않는다.
5. 최종 보고서에 "가정" 절을 둔다 — 사용자가 확인하지 않은 가정이 결과에 영향을 줬는지 알 수 있게.

## 0단계: 기존 실행 확인

- "이어서 stack/dia만", "QA만 다시", "같은 결과로" → 이전 `_workspace*/runs/<obj>_*/`와 `04_ezphot-runner_report.md`의 `<iso>` 경로를 찾아, `<iso>`가 아직 있으면 그 위에 이어서 계획한다.
- `<iso>`가 지워졌으면 처음부터(사용자에게 알린다).
- 새 대상이면 처음부터.

## 1단계: 입력·계획 (리더)

1. 사용자에게 받을 것(없으면 묻는다): 대상 이름, RA/Dec, 관측소·망원경, 필터, 날짜 범위, 원하는 산출물(측광만 / 스택 / DIA / 광도곡선 / 갤러리).
2. `ezphot-recipes` 「입력 고르기」대로 실제 scidata를 읽기 전용으로 탐색해 FITS 목록을 만든다. 개수·필터·날짜 분포를 사용자에게 보여 주고 범위를 확정한다.
   DIA면 reference 후보를 실제 refdata에서 찾아 사용자에게 고르게 한다.
3. `_workspace/03_plan.md`를 쓴다(`ezphot-recipes` 「명령 구성」):
   - 입력 목록 파일 경로, 입력 디렉터리(사후 검사 인자), reference 경로
   - 단계별 명령(격리 경로는 `<iso>`), `--n-proc`, 단계 사이 중단 기준(예: process_images 성공률 < 80%, qa 실패율 > 30%이면 멈춤)
   - 예상 디스크·시간, 현재 `df -h`·`uptime`
   - sky catalog 캐시 갱신 가능성
   - 갤러리 필요 여부
   - 실행 모드(격리/실제 아카이브). 실제 아카이브 모드면 승인 대상 타일 목록, `--real-pre` 대상 디렉터리, 덮어써질 기존 산출물 목록

## 2단계: 안전 감사

**실행 모드:** 서브에이전트 위임

`Agent(subagent_type: "ezphot-safety-auditor", prompt: "측광 실행 계획 / _workspace/03_plan.md / 판정을 최종 메시지로")` → `_workspace/03_ezphot-safety-auditor_verdict.md`.
차단 명령은 고쳐서 재감사한다.

## 승인

측광 실행은 시간·디스크를 크게 쓴다. 판정과 함께 입력 수, 단계, 예상 디스크·시간, 산출물 보존 위치를 사용자에게 보여 주고 **승인받은 뒤** 3단계로 간다.
실제 아카이브 모드는 **대상 타일마다** 따로 승인받고, 승인 내용(타일, 필터, 날짜 범위, 단계, 덮어써질 산출물)을 `_workspace/00_input/request.md`의 "## 승인"에 그대로 적는다.
승인이 일부 타일에만 있으면 그 타일만 실제 아카이브 모드로, 나머지는 격리 모드로 계획을 나눈다.

## 3단계: 실행

**실행 모드:** 서브에이전트 위임

`Agent(subagent_type: "ezphot-runner", prompt: "측광 실행(격리|실제 아카이브) / 계획·판정 경로 / 허용 명령만, 중단 기준 준수 / 격리면 <iso> 보존 / 요약은 _workspace/runs/<obj>_<tag>/ / 보고서: _workspace/04_ezphot-runner_report.md")`.
- 실제 아카이브 모드의 `--real` 검사에 `DELETED`가 나오면 → **모든 작업 중단**, 즉시 보고.
- 사후 검사 엄격 출력 → **모든 작업 중단**, 즉시 보고.
- 중단 기준에 걸려 멈췄으면 → 4단계(QA)로 원인 판단을 받은 뒤 사용자와 계속 여부를 정한다.

## 4단계: 측광 QA

**실행 모드:** 서브에이전트 위임

`Agent(subagent_type: "photometry-qa", prompt: "측광 실행 결과 / 러너 보고서·_workspace/runs/<obj>_<tag>/·<iso> 경로·대상 정보 / 최종 메시지로")` → `_workspace/05_photometry-qa_report.md`.
단계별로 나눠 실행했다면(process_images 먼저, 승인 후 stack/dia) 단계마다 QA를 받는다.

## 5단계: 보고·갤러리

1. `_workspace/06_report.md`와 사용자 요약:
   - 입력(수, 필터, 날짜), 실행 단계와 결과(성공률, qa 통과율)
   - 대상 측광 요약(target 측광표 경로, 주의 행: SATDIST, sentinel)
   - QA 판정 요약과 사용자 판단이 필요한 선택지
   - 사후 검사(엄격·CATALOG·INFO)
   - `<iso>` 경로·크기 — 보존 중이며 삭제는 사용자 결정
2. 사용자가 갤러리를 원하면 `ezphot-recipes` 「갤러리 보기」로 서버를 띄우고 주소를 알린다. 다 보면 내린다.

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 입력이 하나도 없음 | 탐색 경로·조건을 사용자에게 보여 주고 다시 정한다. 추측으로 넓히지 않는다 |
| 디스크 부족 예상 | 실행 전에 범위를 줄이거나 이전 `<iso>` 삭제를 사용자에게 제안 |
| 서브에이전트 실패 | 한 번 재시도. 감사는 필수라 또 실패하면 진행하지 않고 보고 |
| 사용량 한도·권한 거부 | 재시도하지 않는다. runner 로그로 진행 범위를 확인해 기록하고 보고 |
| 감사 차단 | 우회 명령을 만들지 않는다 |
| 사후 검사 엄격 출력 | 전면 중단·즉시 보고. 아무것도 지우지 않는다 |
| 레시피 자체의 버그로 보임 | 실행을 멈추고 증상·로그를 정리해 `ezphot-change`로 넘길지 사용자에게 묻는다 |

## 테스트 시나리오

### 정상 흐름
요청: "T05785 m650·m675 2024-10-30 측광하고 광도곡선 뽑아줘."
1. 리더가 scidata에서 FITS 6장(필터당 3장)을 찾고 목록·디렉터리를 계획에 적는다. 산출물: process_images + qa + target_photometry + visualize.
2. 감사: 조건부(승인, `--pre` 대상 2개 디렉터리, 캐시 갱신 가능성 낮음).
3. 사용자 승인 → runner: `--pre` → process_images(6/6 성공) → qa 통과 → target_photometry → visualize → 사후 검사 clean → 요약 복사, `<iso>` 보존.
4. photometry-qa: ZP 산포·seeing 정상, SATDIST 경고 없음.
5. 보고 + 갤러리 서버(사용자 요청 시).

### 오류 흐름 — 중단 기준
process_images 성공률 50%(platesolve 실패 집중). runner가 중단 기준으로 멈춤 → photometry-qa가 실패 프레임의 공통점(특정 망원경·날짜) 정리 →
리더가 사용자에게 "해당 프레임 제외 후 계속 / `--no-platesolve`로 재실행 / 코드 문제로 ezphot-change" 선택지를 제시.
